## Assumptions
- A1. No Anthropic key and no Supabase project yet (user's choice: connect after the build, with a guide). So: storage sits behind an interface with a local file store as default and a Supabase adapter that activates when the env vars are set; the Claude reader is built with the SDK and unit-tested with a mocked client; the sample waitlist ships with saved readings so everything runs offline.
- A2. Plan Step 1 (stale tags) needs "gone" and "end date" readings that Step 2 produces. Feature 1 takes readings as an input; its test supplies them. Feature 2 then supplies them for real.
- A3. Staff login (Supabase Auth) and Supabase Realtime only work once Supabase is connected. Local mode runs without login on localhost and syncs open tabs by polling.
- A5. **User decision (Oct 29):** the week schedule (A4) is an interactive mockup with made-up data, like `reference/mockups/A4-Week-schedule.dc.html`. It does not read the booking export or connect to Kneadly (not possible). This narrows plan §6 Screen 4, which says "from the booking export".
- A6. **User decision (Oct 29):** the openings, the waitlist (and people's availability) and the booking export are all in the same time zone, the clinic's. File times are used as written, never converted. Only the app's own clock (Booked timestamp, "today", "cancelled at: now") is turned into the clinic's local day, because a hosted server runs in UTC. Feature 7 makes the clinic time zone one setting (now `America/Moncton` in `src/lib/format.ts` and `src/lib/import.ts`).
- A4. Step 6 is split into four features (6a–6d) because it is too large for one pass; README and the section 7 done checks are feature 7.
